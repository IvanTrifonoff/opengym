# openGym — тестирование (для разработчиков и ИИ-агентов)

Эта дока — единственный источник правды о том, **какие тесты есть**, **что они
покрывают** и **как запускать** проект локально и в CI. Если ты агент и пришёл
сюда «разбираться» — начни с раздела «Карта тестов», затем «Как запускать».

---

## Быстрый старт

```bash
# фронтенд: unit-тесты чистой бизнес-логики + сборка
cd frontend && npm test && npm run build

# API: юнит-тесты чистой логики (без БД)
cd api && node --test logic.test.js

# API: юнит + интеграционные тесты слоя БД (нужна живая postgres!)
DATABASE_URL=postgres://u:p@host:5432/db node --test logic.test.js admin-db.test.js

# либо одной командой через npm (требует postgres для admin-db.test.js)
cd api && npm test
```

## Карта тестов

| Файл | Тип | Что покрывает | Нужна БД? | Кол-во |
|---|---|---|---|---|
| `frontend/src/lib/*.test.js` (7 файлов) | unit (vitest) | расчёт усилия RIR/RPE, прогрессия, история, 1ПМ, импорт, демо-данные, wakelock | нет | **192** |
| `api/logic.test.js` | unit (node:test) | чистая бизнес-логика (валидация расписания, переходы брони, слоты дня, routine-id, вебхук) | нет | **33** |
| `api/admin-db.test.js` | integration (node:test) | слой БД: лояльность, брони/конфликты, расписание тренера, инвайты, назначение тренера | **да** (`DATABASE_URL`) | **8** |
| `api/logic.js` | модуль | извлечённая из `server.js` чистая логика — **импортируется** `server.js`, НЕ копия | — | — |

Итого (CI): **192 фронт + 41 api = 233 широких проверки**, из них 8 требуют postgres.

> Оговорка: это покрывает **чистую логику и слой БД**. HTTP-маршруты `server.js`,
> WebAuthn-сессия, push-доставка и миграции проверяются вручную end-to-end на
> дев-стенде. Если добавляешь новый endpooint — покрой его хотя бы через
> `admin-db.js` (интеграционно) или вынеси логику в `logic.js`.

## Архитектура тестов

### Почему `api/logic.js`?
`server.js` — монолит на ~1930 строк: при импорте он **сам слушает порт**, читает
секрет и поднимает пул БД. Юнит-тестировать его напрямую небезопасно. Поэтому
чистая, детерминированная бизнес-логика вынесена в отдельный модуль
`api/logic.js` **без побочных эффектов** (нет I/O, нет глобального состояния).
`server.js` теперь **импортирует** эти функции из `logic.js`, так что это один и
тот же код.

Правило (важно не нарушать):
- В `logic.js` — только чистые функции (детерминированные, без БД/env/сети).
- Всё, что требует поднятой БД/push/env, остаётся в `server.js` или в
  интеграционных тестах `admin-db.test.js`.

### Роут-модули (`api/routes/`)
`server.js` — роутер + сессии + сборка. Обработчики HTTP разнесены по доменам в
`api/routes/*.js` как фабрики, возвращающие `[{ method, path, handler }]`:

- `webhook.js` — внешние интеграции (турникет/лояльность вебхуки)
- `notifications.js` — центр уведомлений (спортсмен + тренер/админ)

Каждая фабрика получает зависимости (хелперы БД/сессий) через аргумент `deps` —
модуль не тянет server.js, его можно юнит-тестировать и править изолированно.
Паттерн для новых доменов: `admin.js`, `trainer.js`, `athlete.js`, `loyalty.js`
— по той же схеме (фабрика → регистрация в server.js → тесты).

### Почему `admin-db.test.js` интеграционный?
`admin-db.js` ходит в postgres. Тесты поднимают реальную схему через миграции
(`adminDbReady`, идемпотентны) и проверяют честное поведение БД: конфликт брони,
накопление баллов лояльности, разрывной график расписания. **Без `DATABASE_URL`
этот файл скипается** (не падает) — так локальный быстрый `npm test` не требует
БД, а в CI БД всегда поднята.

## Интеграционные тесты (postgres)

**Локально** (из `api/`):
```bash
docker run --rm -p 5433:5432 -e POSTGRES_USER=g -e POSTGRES_PASSWORD=g -e POSTGRES_DB=g postgres:16-alpine
DATABASE_URL="postgres://g:g@127.0.0.1:5433/g" node --test admin-db.test.js
```

**В CI** (`ci.yml`) поднимается `postgres:16-alpine` как service, и
`DATABASE_URL` указывается на него. Просто убедись, что service-блок остаётся.

Изоляция: каждый тест использует **уникальные id/тренеров** (префикс `tr_<rand>`)
и **чистит за собой в `finally`** — повторные прогоны чисты и не задевают другие
данные. Свою схему тесты **не** трогают: миграции идемпотентны (`IF NOT EXISTS`).

## Добавление нового теста

1. **Чистая логика** → положи функцию в `api/logic.js` + тест в `api/logic.test.js`
   (node:test). Импортировать из `./logic.js`.
2. **Слой БД** → тест в `api/admin-db.test.js`, оберни в `if (!needDb(t)) return;`,
   используй уникальные id и `finally`-подчистку.
3. **Фронтенд-логика** → по путив `frontend/src/lib/*.test.js` (vitest).
4. Прогони локально + убедись, что в `ci.yml` команда покрывает новый файл
   (для api — `node --test logic.test.js admin-db.test.js`).

## CI/CD (GitHub Actions)

### CI (`ci.yml`) — на каждый push в `dev`
- frontend: `npm test` (vitest 192) + `npm run build`
- api: `node --test logic.test.js admin-db.test.js` против postgres-сервиса
- Проверка синтаксиса `server.js` + `logic.js` (`node --check`)
- **НЕ деплоит** — только сигнал готовности.

### CD (`cd.yml`) — вручную через workflow_dispatch
- Доступен только когда **ты** запускаешь его вручную (Actions → «CD — deploy to prod»).
- Ввод: `app_ref` (обычно тег `vX.Y.Z` из `main`), опционально `seed_data_from`.
- По SSH гоняет `bootstrap.sh` на прод и делает смоук (`/api/health`).
- **Требуемые секреты** в репозитории: `PROD_HOST`, `PROD_USER`, `PROD_SSH_KEY`,
  `PROD_DOMAIN`.

### Версионность (`VERSIONING.md`, `scripts/release.sh`)
- Единый источник истины — **git-тег семвер `vX.Y.Z`**.
- В `main` код попадает **только** через `scripts/release.sh`
  (build+тесты, синхронный бамп `frontend/package.json` + `api/package.json`
  + блок в `CHANGELOG.md`, тег, вливание в `main`, push).
- Прод `impulse.trfnv.ru` стартует с **`v1.0.0`**.

## Частые ошибки и подводные камни

- **`npm test` в api падает с admin-db без БД?** Не должен: `needDb(t)` скипает.
  Если упал — значит забыл `if (!needDb(t)) return;` в начале интеграционного теста.
- **node:test не прерывает выполнение после `t.skip()`.** После skip ОБЯЗАТЕЛЬНО
  `return` из функции теста (см. паттерн `needDb`), иначе код продолжится и упадёт.
- **Поля из `admin-db.js` — snake_case** (`trainer_id`, `user_id`), не camelCase.
- **`web/` директория**: на самом деле прод-фронт строится **корневым `Dockerfile`**
  (который собирает `frontend/`), а не `web/Dockerfile`. `web/` содержит только
  `nginx.conf`. Не путай при чтении compose-файлов.
- **Медиа** закоммичены в репо (`media/img`, `media/gif`) — внешний датасет не нужен.
- Рабочий прод-стек в корне — **`docker-compose.prod.yml`** (самодостаточный:
  db+redis+api+web в одной сети, наружу только host-nginx).
