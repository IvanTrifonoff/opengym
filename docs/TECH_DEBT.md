## 1. Сплит-брэйн хранилища: JSON-файлы атлетов + PostgreSQL для всего остального

**Где:** атлеты хранятся в `./data/state-<uid>.json` + `db.json` (users/creds/
subs/invites), а админка/лояльность/аналитика/расписание — в PostgreSQL
(29 таблиц, см. AGENT_GUIDE.md).

**Риск (транзакционная целостность):** операция, которая пишет в оба хранилища
(например, оплата абонемента: статус в JSON, платёж в PG), не атомарна. Если
сервер «моргнёт» между двумя записями — данные разъедутся. Сейчас это смягчено
тем, что финансовых операций нет, а сбои записи ловятся (atomicWrite + catch).

**План миграции (после запуска):**
1. Таблица `athlete_state` (user_id PK, state JSONB, updated_at) в PG.
2. Дабл-райт на этапе перехода (пишем в файл и в таблицу, читаем из таблицы).
3. Обратная миграция state-файлов в таблицу, выключение файлового слоя.
4. Свести все остальные таблицы в единый контур транзакций.

## 2. Нативный http-сервер без фреймворка (~850 строк server.js + routes/*)

**Где:** `api/server.js` — роутинг вручную через `{ method, path, handler }` +
`readSession`/`requireAdmin`, без Express/Fastify/Koa.

**Почему так:** минимум зависимостей, быстрый старт, никакого оверинжиниринга
на малой нагрузке. Для текущего масштаба это плюс, а не минус.

**Риск (поддержка):** когда появится сложная авторизация на разных роутах,
валидация payload'ов, rate-limiting на уровне приложения — ручной роутер станет
больно поддерживать (middleware приходится эмулировать в каждом хендлере).

**План (когда проект начнёт расти):** переезд на Fastify (или Express) с
нормальными middleware-цепочками (auth, validation, rate-limit), сохранив
фабричную структуру `routes/*.js` (они уже принимают deps — перенос будет
механическим).
