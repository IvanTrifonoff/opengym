# Multi-Tenant: Клубы → Филиалы → Роли (design doc, v1.3.x)

Статус: **согласовано** (2026-09-06). Этап реализации: не начат.
Авторы: владелец продукта + системный архитектор (ревью) + агент.

## 1. Проблема (что сейчас не так)

- Нет сущности «клуб»: `branches` — плоский список `id, name` без родителя
  и без владельца. Филиалы «создаются в воздухе».
- Роль `owner` одна на всю платформу; нет владельца конкретного клуба.
- `scopeAdmins()` фильтрует сотрудников только по `demo_session`: на проде
  менеджер, тренер и оператор видят ВСЕХ сотрудников и все филиалы.
- Инвайт сотрудника (`createAdminInvite`) не сохраняет `branch_key`/клуб,
  а `registerAdmin` пишет `admin_users` без них. Новый менеджер получает
  `branch_key = null`, что в `analyticsScope` означает «вся сеть».
- Атлеты живут в JSON (`db.users`/`state-<uid>.json`) без club/branch-поля;
  филиал выводится на лету из loyalty-событий посещений — медленно и неточно.

## 2. Целевая модель

```
superadmin (владелец платформы, club_id = null) — полный доступ ко всем клубам
 └── club (клуб)
      ├── owner (владелец клуба, club_id ОБЯЗАТЕЛЕН)
      ├── manager (менеджер, branch_key ОБЯЗАТЕЛЕН)
      ├── operator (чтение в своём клубе/филиале)
      ├── trainer (только свои атлеты)
      └── athlete (приложение; club_id/branch_key пишутся при регистрации)
branches.club_id → club
admin_users.club_id → club   (superadmin: null)
```

### Роли и права

| Роль | Видит | Управляет |
|---|---|---|
| `superadmin` | все клубы, все филиалы, всех сотрудников | вкладка «Клубы», всё |
| `owner` | свой клуб (club_id обязателен) | сотрудники/филиалы/лояльность/аналитика своего клуба, «войти как» внутри клуба |
| `manager` | свой филиал (branch_key обязателен) | сотрудники филиала, лояльность филиала, заявки, аналитика филиала |
| `trainer` | только своих атлетов | программы, расписание, удержание своих атлетов |
| `operator` | чтение своего клуба/филиала | ничего |

### Ключевые правила безопасности (из ревью архитектора)

1. **Не перегружать роль `owner`.** Вводится роль `superadmin` — владелец
   платформы (Ivan), `club_id` может быть null. Роль `owner` — владелец
   конкретного клуба: `club_id` **обязателен**. Если у `owner` нет `club_id` —
   сервер отвечает 403/500, а НЕ даёт доступ ко всей платформе. Это исключает
   повышение привилегий при случайном сбросе `club_id` в null.
2. **club_id атлета пишется в state-<uid>.json в момент регистрации** по
   инвайту (инвайт несёт club_id/branch_key, либо наследуется от тренера через
   `trainer_assignments`). При старте сервера `db.users` индексируется по
   `club_id` в памяти, чтобы аналитика клуба считалась мгновенно, а не из
   событий визитов.
3. **Миграция бесшовная** (ниже), прод не простаивает.

## 3. План миграции (Safe Migration Strategy)

### Шаг 1 — Схема (Postgres, аддитивно)
- `CREATE TABLE IF NOT EXISTS clubs (id TEXT PRIMARY KEY, name TEXT NOT NULL, owner_admin_id TEXT, created_at TIMESTAMPTZ DEFAULT now(), deleted_at TIMESTAMPTZ)`
- `ALTER TABLE branches ADD COLUMN IF NOT EXISTS club_id TEXT`
- `ALTER TABLE admin_users ADD COLUMN IF NOT EXISTS club_id TEXT`
- Индексы по `branches.club_id`, `admin_users.club_id`.

### Шаг 2 — Бэкфилл данных
- Скрипт создаёт клуб-заглушку «Club #1» (текущий живой клуб).
- Проставляет `club_id` всем существующим `branches` и всем `admin_users`
  (кроме superadmin'а).
- Аккаунту владельца платформы меняется роль на `superadmin`.
- Итог: данные консистентны, код пока работает по-старому (роль `superadmin`
  обрабатывается как прежний `owner` — это совместимо).

### Шаг 3 — Scoping (backend)
- `scopeAdmins`, `scopeBranches`, `scopeOwnerRows`, `analyticsScope`,
  `GET /api/admin/staff`, инвайты, аналитика, retention, лояльность —
  становятся club/branch-aware.
- `club_id` обязателен на уровне приложения для `owner`/`manager` (иначе 403).
- Тесты на каждое правило (роль → видимость).

### Шаг 4 — UI
- Вкладка «Клубы» только для `superadmin`: создать клуб, назначить владельца,
  управлять филиалами клуба.
- В форме инвайта сотрудника — обязательный выбор клуба/филиала.
- Шапка админки показывает контекст клуба; менеджер/оператор/тренер видят
  только свой срез везде.

### Шаг 5 — Trial-клубы: демо-стенд как лидогенерация (NEW, согласовано)
Механика анонимного демо заменяется на Trial с email-лидогенерацией.
Флоу:
1. Промо-страница: клиент вводит email → «Создать мой клуб».
2. Бэкенд создаёт **реальный изолированный Club** (флаг `is_demo=true` /
   `trial_until`), наполняет его данными (пара тренеров + атлетов, правила
   лояльности, награды — переиспользуется `spawnDemoClub` из demo-club.js,
   но пишет в `clubs` вместо demo_session).
3. Генерируется **owner-инвайт** (magic link) именно для этого club_id:
   `createAdminInvite` сейчас запрещает роль `owner` (admin-db.js:416) —
   для триала нужен отдельный путь, разрешающий owner + club_id.
4. **Resend** (`email.js`, уже в стеке): клиенту письмо «Ваш фитнес-клуб
   готов!» со ссылкой на регистрацию (passkey). Параллельно лид дублируется
   супер-админу («Новый лид … запросил демо») — существующая связка
   promo_leads + notification + email.
5. Клиент по ссылке проходит штатную passkey-регистрацию сотрудника
   (`/admin/staff/register/options` + `verify`, роль owner) и входит как
   **owner своего клуба**: без вкладки «Клубы», видит только свой бизнес,
   плодит филиалы/тренеров/атлетов (это обеспечивает Шаг 3-скоуп).
6. **Trial TTL 7–14 дней** вместо 60-минутных demo-сессий. Покупка = снять
   флаг триала, клуб продолжает жить. Автоочистка — ночной cleaner по
   `trial_until` (аналогично runDemoCleanupOnce).

Зависимости: Шаги 1-4 (clubs + club_id + скоуп + UI) ДО этого шага.
Нюансы: антибот на форме (PoW из demo-pow.js или rate-limit как в
routes/leads.js); owner-инвайт одноразовый, срок жизни ~7 дней; email-домен
send.trfnv.ru уже верифицирован в Resend.

### Релиз
Каждый шаг: версия, CHANGELOG, build, автотесты, commit, push, деплой прод+демо.

## 4. Обратная совместимость

- `superadmin` обрабатывается везде, где раньше был `owner` (owner+club_id=null
  больше не используется).
- Демо-клоны (`demo_session`) остаются ортогональными: `scopeAdmins` и др.
  фильтруют и по `demo_session`, и по клубу.
- Старые `owner`-аккаунты без `club_id` при миграции получают клуб #1 (или
  блокируются, если не superadmin).
