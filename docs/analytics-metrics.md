# Тренировочные метрики (athlete_metrics) — архитектура данных аналитики

> Для агентов: читай этот файл перед тем, как трогать аналитику или хранение
> тренировок. Здесь объяснено, **почему** данные лежат в двух местах и как они
> синхронизируются.

## Проблема, которую решает

Полная история тренировок спортсмена живёт в **per-user JSON-файлах**
(`data/state-{uid}.json`: workouts, bodyweight, routines, unit, …). Это источник
правды для приложения спортсмена (`GET/PUT /api/data`).

Раньше аналитика (обзор / список / лидерборд в админке) читала и парсила **все**
эти файлы с диска на каждый запрос — N синхронных `readFileSync` в одном
запросе (`collectAnalytics` вызывал `stateOf(uid)` для каждого спортсмена).
При 1000 атлетов и годе истории это больно на каждом открытии вкладки.

## Решение: денормализованные агрегаты в PostgreSQL

| Слой | Что хранит | Кто читает |
|---|---|---|
| **Файлы** `state-{uid}.json` | Полная история спортсмена (workouts целиком, подходы, вес тела, программы) | Только сам спортсмен: `GET/PUT /api/data` — 1 файл на пользователя, это дёшево. Плюс drill-down одного спортсмена (`athleteDetail` — 1 файл) |
| **PostgreSQL** `athlete_metrics` | Агрегаты по дням: `(user_id, day, workouts, volume, sets, exercises)` | Аналитика по всем: `collectAnalytics` (overview / athletes / leaderboard) — один SQL `GROUP BY` вместо N файлов |
| **Redis** | Ничего из истории — он для мелкого горячего (сессии/рейт-лимиты) | — |

`volume` = сумма (вес × повторения) выполненных подходов за день — та же
семантика, что у `workoutVolume()` в `api/analytics.js`.

## Как обновляется

1. **После сохранения тренировки** (`PUT /api/data` в `server.js`):
   `replaceAthleteMetrics(user.id, body.state)` — DELETE всех строк спортсмена +
   batch INSERT текущих дней из state, в одной транзакции. Полная перезапись —
   осознанный выбор: файл одного спортсмена — источник правды, его размер
   (десятки–сотни тренировок) делает пересчёт дешёвым, а удаления тренировок
   автоматически исчезают из метрик. Ошибка БД не роняет сохранение (try/catch).
2. **При старте api**: `backfillAthleteMetrics({ users, stateOf })` — разовый
   пересчёт по всем пользователям из state-файлов (страховка для тех, кто
   сохранялся до появления таблицы). Логируется: «metrics backfill done: N ok».
3. **Вручную**: `replaceAthleteMetrics` идемпотентна, можно звать повторно.

## Как читается аналитикой

`pgAggregates()` в `api/analytics.js` добавляет к существующим запросам 4 по
`athlete_metrics` (все — одним `GROUP BY`, параллельно через `Promise.all`):

- `metricsByUser` — всего: workouts, volume, `max(day)` (последняя тренировка)
- `metrics30ByUser` — за последние 30 дней: workouts30, volume30
- `metricsPrevByUser` — за окно 30–60 дней назад: volume30Prev (тренд тоннажа)
- `weekKeysByUser` — ключи недель с тренировками
  (`to_char(date_trunc('week', day), 'IYYY-IW')`) для серии недель

`athleteRow(u, pg, now, S)` больше **не читает workouts из state**: все
тренировочные агрегаты берутся из метрик. `S` передаётся только из
`athleteDetail` (drill-down) — для `unit` и веса тела; в списке спортсменов
`bw`/`bwDelta30` равны `null` (фронт их в списке не показывает).

## Ограничения и будущее

- **Единицы**: в `athlete_metrics` единицы не хранятся — в списке/лидерборде
  `unit` = `'kg'` по умолчанию. Drill-down показывает правильный `unit` из state.
  Если появятся спортсмены с lb в лидерборде — добавить колонку единиц.
- **Серия недель**: считается в JS из ключей недель (см. `streakFromWeeks`),
  а не в SQL. На стыке годов возможна погрешность ISO-года (`getFullYear` vs
  `IYYY`) — для серии это 1–2 дня в году, не влияет.
- **`access_events`** (журнал СКУД) растёт безгранично — нужен retention
  (архив/удаление старше ~90 дней), см. TODO в `access-db.js`.
- Метрики не покрывают: вес тела, лучшие веса, недельный график drill-down —
  они остались на state-файлах (1 файл на спортсмена — это ок).
