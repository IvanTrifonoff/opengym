## Шаг 4 — UI и интерфейсы

### 1. Утечка списка филиалов (жёсткое отсечение на бэкенде)

**Текущее состояние (уже сделано в Шаге 3):** `GET /api/admin/branches` НЕ
отдаёт «весь список из базы». Хендлер в routes/admin.js вызывает
`scopeBranches(admin, await listBranches())` прямо перед `json()`:

```js
// routes/admin.js
{ method: 'GET', path: '/api/admin/branches', handler: async (req, res) => {
    const admin = await requireAdminAccount(req, res); if (!admin) return;
    json(res, 200, { branches: scopeBranches(admin, await listBranches()) });
} }
```

А `scopeBranches` (demo-scope.js) жёстко фильтрует **на сервере, до ответа**:
- manager → `rows.filter(r => r.id === admin.branch_key)` — ТОЛЬКО свой филиал;
- owner/trainer/operator → `r.club_id === admin.club_id` — только клуба;
- superadmin → все живые (это его легитимный срез);
- без club_id → `[]` (strict-mode, никакого «всего»).

**Вывод:** в Network-табе менеджер физически не увидит чужих филиалов — их нет
в теле ответа. Фронтенд не фильтрует, он только отрисовывает то, что пришло.
Форма инвайта возьмёт филиалы из этого же эндпоинта → менеджеру доступен лишь
его собственный. Защита держится на backend-scope, а не на скрытии в UI.

**Дополнительно для Шага 4** (слой «клуб → его филиалы» в UI супер-админа):
вводим `GET /api/admin/clubs/:id/branches` (superadmin/owner этого клуба) —
тот же `scopeBranches`, но с явным клубом. Переиспользуем одну функцию скоупа,
никакого второго пути выгрузки.

### 2. Kill Switch («Заморозить/Отключить» клуб)

**Проблема подтверждена:** в `clubs` сейчас нет `is_active`/`status` — только
`id, name, owner_admin_id, created_at, deleted_at`.

**Решение — колонка `status` + «заморозка», а не удаление:**

- Миграция (аддитивная, идемпотентная, в adminDbReady):
  ```sql
  ALTER TABLE clubs ADD COLUMN IF NOT EXISTS status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','frozen','deleted'));
  ```
- `frozen` — бизнес-эквивалент deleted_at для неоплаты: клуб существует, данные
  целы (чтобы после оплаты всё вернулось), но **доступ всему персоналу закрыт**.
- **Блокировка на уровне ядра, не только UI:** в `requireAdminAccount`
  (server.js) после проверки роли добавляется:
  ```js
  if (admin.club_id) {
    const club = clubCache.get(admin.club_id);          // см. ниже про кэш
    if (club && club.status === 'frozen')
      return json(res, 403, { error: 'club suspended — contact support' });
  }
  ```
  Это «рубильник»: один UPDATE в БД → 403 каждому owner/manager/trainer/
  operator клуба на **каждый** `/api/admin/*` запрос. Спортсмены (app, не
  админка) продолжают видеть свои тренировки (их данные — их собственность),
  но клубные скоупы/награды/пуши тренера гаснут по правилам Шага 3 (роль
  сотрудника 403 → тренер не тянет данные).
- **Кэш статусов клуба** (см. п.3) нужен и здесь: requireAdminAccount
  выполняется на каждый запрос, читать clubs из PG каждый раз дорого.
  Обновление через TTL-кэш (например, 30–60 c) — «заморозка» срабатывает
  практически мгновенно, но без per-request SELECT.
- UI: в списке клубов у superadmin появляется переключатель
  Активен/Заморожен (`POST /api/admin/clubs/:id/status`, superadmin-only) +
  плейсхолдер причины. Название «Заморозить» вместо «Удалить» — данные
  сохраняются, что критично для B2B (клиент может вернуться).

### 3. Пагинация списка клубов

**Проблема подтверждена:** `GET /api/admin/clubs` отдаёт `listClubs()` целиком.

**Решение — курсорная пагинация по умолчанию, без «магического» лимита:**

- `GET /api/admin/clubs?limit=50&before=<id>` (или `after`):
  ```sql
  SELECT id, name, owner_admin_id, status, trial_until, created_at
  FROM clubs WHERE deleted_at IS NULL
    AND ($2::text IS NULL OR id < $2)          -- курсор по id (сортировка DESC)
  ORDER BY id DESC LIMIT $1
  ```
  Плюс `has_more` в ответе (SELECT count итд — или просто
  `LIMIT limit+1` и отдать `has_more = rows.length > limit`).
- id у клубов — случайные hex/base64 (уже так у всех сущностей) → курсор по id
  безопасен и стабилен при вставках.
- Тот же механизм для списка филиалов клуба, когда их станет > 100.
- `trial_until` и `status` добавляются в SELECT (нужны для п.2 и для UI тарифов).
- Фронтенд: «показать ещё»/бесконечный скролл; 500 триалов рендерятся порциями
  по 50, DOM не разрастается.

## Шаг 5 — Trial-клубы и лидогенерация

### 4. Спам/Abuse на Resend: rate-limit по IP + валидация email

**Проблема подтверждена:** PoW один не спасает (спамер может считать хеши).
Уже есть `rateLimit` в routes/leads.js (5/час/IP, in-memory Map) и PoW-механика
в demo.js (`demo-pow.js`, лимит токенов на IP). Но для публичного
trial-эндпоинта, который **шлёт email через Resend**, нужно жёстче.

**Решение — «пирамида» из 4 слоёв (публичный эндпоинт `/api/trial`):**

1. **PoW** (уже в стеке, demo-pow.js): клиент тратит ~2^16 sha256 на challenge —
   отсекает массовых скриптеров без капчи.
2. **Жёсткий rate-limit по IP, в БД а не в памяти**: таблица
   `trial_requests(ip, created_at)` (или переиспользовать паттерн
   `demo_tokens`). Лимит настраивается env'ом:
   - `TRIAL_PER_IP_HOUR` = 2 (максимум 2 клуба с одного IP в час — столько
     реальных клиентов с одной сети не бывает);
   - `TRIAL_PER_IP_DAY` = 5 (страховка от «забыл — попробовал ещё раз»).
   In-memory Map из leads.js не подходит: сбрасывается при рестарте и не
   работает на 2+ инстансах.
3. **Валидация email**: синтаксис (один лёгкий regex, `^[^@\s]+@[^@\s]+\.[^@\s]+$`)
   + **MX-проверка** через `dns.resolveMx` (в Node встроено, без зависимостей):
   домен без MX (одноразовые/фейковые почты) отсекается до создания клуба и
   письма. Плюс блок-лист заведомо мусорных доменов (`mailinator.com` и т.п.,
   небольшой env-список). Это бьёт по «Resend-разорению»: письмо уходит только
   на реально существующий почтовый домен.
4. **Сквозной лимит на отправку** (последний рубеж перед Resend): счётчик
   `trial_emails_sent` за час/день; при превышении эндпоинт отвечает 503
   «try later», даже если 1–3 слоя пройдены. Отдельно — **общий дневной бюджет
   Resend** из панели: сверяемся перед каждой отправкой.

Дополнительно: письмо владельцу клуба уходит **с задержкой и ретраем** (уже
паттерн dispatchOutbox из пуша), чтобы сбой Resend не ронял trial-флоу.

### 5. «Проблема 15-го дня»: GC просроченных триалов

**Механика (по образцу демо, уже есть):** в демо-стеке каждые 5 минут бежит
`startDemoCleaner` → `runDemoCleanupOnce` → `destroyDemoClub` для сессий с
истёкшим `expires_at` (demo-club.js:54–75). Для триалов тот же паттерн, но с
**двумя режимами**, потому что «сжечь данные» при неоплате нельзя (вдруг
клиент вернётся):

- Таблица `clubs` получает колонки:
  ```sql
  ALTER TABLE clubs ADD COLUMN IF NOT EXISTS trial_until TIMESTAMPTZ;
  ALTER TABLE clubs ADD COLUMN IF NOT EXISTS plan TEXT NOT NULL DEFAULT 'trial';
  ```
  `plan` ∈ {`trial`, `start`, `network`, `selfhosted`} — будущие тарифы.
- **Фоновый воркер** (в api-контейнере, аналогично `runDemoCleanupOnce`):
  каждые N минут выбирает `SELECT id FROM clubs WHERE plan='trial'
  AND trial_until < now()` и:
  - **не удаляет** клуб, а переводит `status='frozen'` (тот же kill-switch из п.2
    — одна механика на два сценария: неоплата и конец триала);
  - шлёт владельцу письмо «триал истёк — данные сохранены 30 дней, продлите,
    чтобы продолжить» (Resend);
  - через **grace-период** (например, 30 дней, env `TRIAL_GRACE_DAYS`) frozen-
    триал удаляется полностью тем же destroy-механизмом (клуб + филиалы +
    сотрудники + атлеты-`state`-файлы + связанные PG-строки).
- **Проверка при логине тоже есть** (не только воркер): `requireAdminAccount`
  из п.2 смотрит `status` → frozen даёт 403. Воркер и логин-проверка
  перекрывают друг друга: если воркер проспал (контейнер лежал), клиент не
  войдёт — «проблемы 15-го дня» нет даже при пропуске GC.

### 6. «Грязные» демо-данные в купленном клубе

**Проблема подтверждена:** spawnDemoClub наполняет клуб фейковыми тренером
и атлетами. После покупки владельцу нужны чистые данные, но нельзя отличить
«тестового Василия» от реального клиента, которого владелец завёл сам.

**Решение — «демо-песочница» отделена от живых данных структурно:**

1. **Сегрегация по именам ид-шников при спавне** (уже частично так у демо:
   `demo-owner-<sid>`, `demo-trainer-<sid>`, атлеты `demo-artem-<sid>` и т.д.).
   Для триала вводим **единый префикс-константу `trial_`** для всех сущностей
   спавна: админ-записи, атлеты в db.json, их `state-*.json`, loyalty-правила,
   брони. Тогда «что создано спавнером» определяется одним SQL/фильтром по
   префиксу, а не списком имён.
2. **Демо-данные помечаются при создании** полем `is_seed=true`:
   - атлеты: `u.is_seed = true` (в db.json);
   - админ-записи: колонка `admin_users.is_seed BOOLEAN DEFAULT false`;
   - правила/награды/брони: отдельная колонка или выводимость из `created_by`
     (`trial-owner-...`) — предпочитаю явную колонку, выводимость хрупкая.
   Владелец при регистрации (первый вход) помечается `is_seed=false` — его
   записи и записи, созданные после триала, «живые».
3. **Кнопка «Очистить демо-данные»** в UI владельца (или автоматически при
   апгрейде до платного тарифа): вызывает `POST /api/club/purge-seed`, который
   удаляет ровно `is_seed=true` записи (и их state-файлы/брони) в транзакции.
   Реальные клиенты владельца не задеты — у них `is_seed=false`.
4. **Бонус для аналитики:** `is_seed` одновременно решает вопрос «фейковые
   цифры в статистике во время демо владельцу» — воркеры retention/удержания
   могут исключать seed-записи из метрик клуба, а владелец видит честные
   цифры даже до очистки. Это же поле — база для отчёта «внедрили, а вот
   динамика после старта».

## Сводка изменений схемы (все аддитивные, zero-downtime)

| Таблица | Колонка | Назначение |
|---|---|---|
| `clubs` | `status` (`active/frozen/deleted`) | Kill-switch (п.2) + конец триала (п.5) |
| `clubs` | `trial_until TIMESTAMPTZ` | TTL триала (п.5) |
| `clubs` | `plan` (`trial/start/network/selfhosted`) | Тариф (п.5, будущие) |
| `admin_users` | `is_seed BOOLEAN` | Отличие фейковых данных спавна (п.6) |
| (db.json users) | `is_seed` | То же для атлетов (п.6) |
| `trial_requests` | `(ip, created_at)` | БД-rate-limit по IP (п.4) |
| (users/state) | префикс `trial_` | Структурная сегрегация спавна (п.6) |

Все миграции — `ADD COLUMN IF NOT EXISTS`/`CREATE TABLE IF NOT EXISTS` без
NOT NULL (кроме внутренних default) в adminDbReady — metadata-only, прод не
блокируют (тот же приём, что в Шагах 1–2).

## Порядок реализации

1. Схема: колонки clubs/admin_users + trial_requests (миграция, тесты).
2. `requireAdminAccount` + клубный kill-switch (status=frozen → 403) + кэш.
3. Пагинация `/api/admin/clubs` (и филиалов клуба).
4. Воркер GC триалов (trial_until → frozen → purge по grace) — по образцу
   runDemoCleanupOnce + тесты на «15-й день».
5. Публичный `/api/trial` (PoW + IP-limit в БД + MX-валидация + бюджет Resend).
6. Trial-спавн с `is_seed`/префиксом + `purge-seed` + UI (Шаг 4 UI поверх).

Каждый пункт: тесты → changelog → версия → commit → push → деплой прод+демо.
